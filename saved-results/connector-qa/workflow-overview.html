How the connector QA workflow works

A runner that talks to the real app on the live Simulator through the real ChatGPT model, the way a person would, several times over, and then refuses to believe the reply until the app's own log agrees with it.

23 connector banks
188 scenarios
9 prompt registers
3 repeats by default
4 verdicts, flaky never rounded up

Why the first attempt failed, and what changed

The naive QA drove each feature once with a test-shaped prompt, then read the reply. It passed things that broke for real users and missed things that only failed sometimes.

Problem 1

Prompts were overly specific. "Read gmail message list, limit 5" works when "anything new in my inbox?" does not, and only the second one is what people type.

Fix

Every connector has a bank of prompts in nine registers: precise, casual, vague, typo, indirect, followup, clarify, decline and write. The unit tests refuse a bank that lacks the required kinds.

Problem 2

Everything ran once. A feature that works from a cold launch but not mid-conversation, or two times in three, looked fine.

Fix

Each scenario runs three times, alternating a fresh app launch with continuing the existing chat. Mixed results are reported as flaky, a real verdict that nobody gets to round up to pass.

Problem 3

The reply was the only evidence. A confident answer that never touched the connector counted as a pass.

Fix

Ground truth is the app's log stream plus the chat store on disk. A reply alone can never pass. The command must appear in the log, the provider must answer 2xx, and no write may fire on a read.

The pipeline

One run is one command. Everything below happens inside it, in this order.

1

Pick scenarios and expand them into steps

Banks live in ios/qa/connector-qa/scenarios/*.json. Filters narrow by connector, kind or id. Each scenario becomes N steps, launches alternate cold and warm, and a followup pulls its predecessor in first. Write prompts get a fresh run marker like qa2026091505030ab1f substituted in.

Produces run.json batch-N.json
2

Boot the Simulator and start the log stream

The live "Operator iPhone 14 Pro" Simulator keeps its Keychain, sign-in and connected accounts. The runner never erases it and only ever upgrade-installs. It streams the app's unified log (subsystem app.operator.ios) to disk for the whole run.

Produces app-log.ndjson
3

Drive batches of 8 through the real chat

An XCUITest driver (ScenarioDriverUITests, only active with OPERATOR_QA=1) types each prompt into the app, waits for the header to go from "Working" back to "Ready" for two consecutive polls, and taps Allow or Cancel on approval sheets by itself. If the app dies it marks the step app-crashed, relaunches, and continues with the next step instead of taking the batch down with it.

Produces batch-N.results.jsonl batch-N.xcodebuild.log
4

Collect ground truth per turn

After each batch the runner cuts a window of log lines from two seconds before the prompt was sent to three seconds after the driver saw the app go idle, and reads the reply from the chat store the app persisted. The store path is resolved again after every batch because a reinstall moves the app's data container.

Produces batch-N.conversation.json
5

Run the mechanical checks

Pure functions, no model. They decide pass, fail or blocked for each step from the log window, the alerts the driver saw and the reply text. The same checks can be replayed offline with rescore after a check or an expectation changes, spending no turns.

Produces results.jsonl judge-input.jsonl report.md
6

Judge what the checks cannot

A fresh LLM subagent that has not seen the run reads every row against judge/rubric.md: did the reply actually satisfy a person who typed that prompt in that register? It may only lower a verdict, never raise one. report --run merges its verdicts into the report.

Produces verdicts.jsonl report.md (merged)
7

Sweep what the run wrote

cleanup --run searches Drive, Calendar, Tasks, Outlook and Slack for the run marker and deletes the matches. It refuses to report a clean sweep when a provider's cleanup test was skipped. Notion pages have no delete tool and must be removed by hand.

Produces cleanup summary in the reply

The mechanical checks, in the order they run

The first check that settles the verdict wins. Blocked means the environment, not the connector, and is never mixed with fail.

  1. driver blocked the driver could not even send the turn (not signed in, permission sheet it cannot answer, rate limit)
  2. app-alive the app crashed during the turn. Always a fail, never blocked
  3. blocked log/reply notConnected, RATE_LIMITED, Keychain errors, "not connected on this device"
  4. reply-present an assistant message for this exact prompt was persisted after it was sent
  5. commands-any at least one expected native command appears in the log window
  6. commands-none no forbidden command ran. Clarify and decline scenarios forbid every write by default even if the bank forgot to say so
  7. operations-any the expected provider operation was requested (skipped when the user denied)
  8. status-2xx and response-seen the provider actually answered, and with success
  9. no-rejected no service-layer rejection such as permissionDenied (a 403 is a fail, not blocked)
  10. approval-seen / approval-denied / no-approval the approval sheet appeared exactly when the scenario says it should, and the tap matched
  11. no-failure-phrase "couldn't", "unable to", "not connected" and friends, negation-aware so "I did not create it because you cancelled" is fine
  12. reply-contains / reply-must-not-contain bank-specific words, such as no "created" after a Cancel
  13. asks-a-question a clarify turn has to end in a question
passEvery repeat passed both the checks and the judge.
flakySome repeats passed, some failed. Reported as its own row, never averaged away.
failEvery repeat failed, or any repeat crashed the app.

The judge

Mechanical checks prove the app did the work. They cannot tell whether the answer was the one the person wanted. That is the judge's only job, and it works under eleven rules in judge/rubric.md. The ones that matter most:

  • Only lower. A judge can turn a mechanical pass into a fail. It cannot rescue a fail.
  • Grade what the app did, not what it said. The row carries the commands, operations and statuses; a reply that contradicts them loses.
  • Satisfaction per register. A vague prompt that got a reasonable interpretation passes. A precise prompt that got a partial answer fails.
  • Clarify must ask, decline must be honest, followup must reuse. Each kind has its own bar in a per-kind table.
  • Oracles. Where a bank gives an oracle ("compare with the newest message in the owner's inbox") the judge uses it.
  • Latency is not a fail. When unsure, fail, and say why in one line.

It runs in a fresh subagent that has not seen the run, so it reasons from the rubric instead of from the operator's expectations. It writes one {stepKey, verdict, reason} per row.

Running it

The whole procedure is a skill, ios/qa/connector-qa/SKILL.md. Codex finds it through the root AGENTS.md; Claude Code through a symlink under .claude/skills. Either agent follows the same eight steps.

Guardrails

  • Money. Every step is one real ChatGPT turn on the owner's personal account, approved on 2026-09-14 for this workflow with no cap. A full pass at three repeats is roughly 600 turns. The dry run prints the count before anything is spent, and the account is written into every run.json.
  • The Simulator is precious. It holds the signed-in ChatGPT session and every connected account in its Keychain. The runner never erases it, never uninstalls, and never builds with signing off.
  • Writes only hit the owner. Every write prompt carries the run marker and targets the owner's own Drive, Calendar, Tasks, Outlook mailbox, Slack DM or Notion. The unit tests reject a write prompt with a foreign address or no marker. WhatsApp never messages an external number.
  • Approval sheets are real. The driver taps Allow on the app's own "Allow account action?" and "Allow Notion action?" sheets, and Cancel when a scenario says deny. System permission prompts from Springboard are answered but never counted as an approval.
  • Stop on rate limits. The runner marks them blocked and aborts after three consecutive errors instead of burning turns.

What it has found so far

Built and exercised on 2026-09-14 and 15 with three smoke runs and three Gmail runs. All of these came out of the runner, not out of reading code.

fail The embedded runtime crashes on some Gmail replies

Reproduced four times across three Gmail runs: the turn after reading an inbox whose subject line contains emoji dies with EXC_BAD_ACCESS on the NodeMobile thread, inside V8's Intl.Segmenter. The lead is openclaw's text-chunking code calling Intl.Segmenter on the reply. The first two runs lost the rest of the batch to it; the driver now relaunches and finishes, so the crash shows up as one failed repeat and the other scenarios still get graded.

flaky A turn hung once and answered on relaunch

In the first smoke run the model streamed its first text at 30 seconds and never reached a terminal event for four minutes. The same prompt answered normally after a cold launch. The third Gmail run hit the same hang three times in 18 turns, with passing turns in between, so it is intermittent and not yet root-caused. Exactly the kind of one-in-N behaviour a single-shot test would miss.

blocked The Simulator moves the app's data container on every reinstall

Two working turns were scored "no reply" because the runner had cached the chat store path at startup. Each XCUITest invocation reinstalls the app and the container id changes. The path is now resolved after every batch, and a memory note records the trap for future sessions.

Adding a connector or a scenario

Create or edit ios/qa/connector-qa/scenarios/<connector>.json with the schema in scenarios/README.md. Each scenario names its kind, the prompt, and an expect block: the outcome (answer, clarify, decline, handoff), which native commands must and must not run, which provider operations, whether an approval sheet is required, and optional reply words and an oracle for the judge. Run the unit tests; they refuse a bank that lacks any of the seven required kinds, a followup without a predecessor, a write without a marker, or a write aimed at anyone but the owner.
