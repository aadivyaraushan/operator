# Operator location tool — implementation notes

**Task:** add a tool that gives the on-phone Codex/operator agent the user's current device location. Verify on the physical Pixel 9 (`4B230DLAQ001Z5`).
**Date started:** 2026-08-25. Governing playbook: Feature (own the design; name the data shape; delegate implementation; verify on the real surface).

## Device grounding (measured, adb, free)
- **Only `com.termux` is installed — NOT `com.termux.api`.** So `termux-location` (Termux:API) is unavailable. Option B (proot -> termux-location) is out unless we sideload Termux:API, which has the same Play-build signature-match problem as Termux:Boot. => **Design A: Android-side FusedLocationProvider surfaced through the broker/RPC is the path.**
- `app.codexlauncher` currently holds **no location permission** (`dumpsys package` shows none). Must add `ACCESS_FINE_LOCATION` + `ACCESS_COARSE_LOCATION` to the manifest and request at runtime.
- Device location providers enabled: `fused provider [u0] enabled`, network + gps present. FusedLocationProvider will return a fix.

## Data shape (to finalize after recon A maps the tool surface)
Provisional tool result the agent receives:
```
location = {
  latitude: Double, longitude: Double,
  accuracyMeters: Float,
  timestampMillis: Long,          // when the fix was taken
  provider: String,               // "fused" | "gps" | "network"
  address: String?,               // optional reverse-geocode (Android Geocoder, no API key)
}
```
Failure shape: a typed error the agent can read (permission_denied | location_unavailable | timeout), never a silent null.

## Open design decisions (surface, don't block)
- Foreground-only fix vs background location. Default: **foreground/on-demand** current fix (agent asks -> app fetches while it holds permission). Background location needs a special Android permission + Play policy justification; out of scope unless asked.
- Fine vs coarse. Default: request fine, fall back to coarse/last-known if fine times out.
- Reverse geocode to a human address. Default: include it best-effort (Android `Geocoder`, offline-capable, no key), omit on failure.

## Recon A — how tools reach the agent (source-grounded)
- Agent tools = OpenClaw plugin `agentbridge/openclaw-plugin/` registering ~77 capability adapters (`src/tools.ts:73`, list = build-time snapshot `src/tools.json` + `openclaw.plugin.json`, regenerated by `scripts/sync-tools.mjs` against a LIVE device). A new adapter is invisible to the agent until sync-tools is rerun on-device and the plugin redeployed.
- Each tool call -> `POST https://127.0.0.1:9443/v1/agent-tools/call` (Go bridge, TLS-pinned, bearer) -> `agentbridge.Bridge` (`bridge.go:228 handleCall`) -> `capability/registry` adapter.
- **Template path (maps):** adapter `adapters/maps/adapter.go` -> Go client `androidbroker/maps/client.go` -> `POST http://127.0.0.1:9451/v1/broker/maps/...` -> Android `BrokerRouter.kt:29` -> `MapsBrokerOps`.
- Manifest today (`AndroidManifest.xml:3-10`): INTERNET, CAMERA, RECORD_AUDIO, POST_NOTIFICATIONS, etc. **No location permission.** No `play-services-location` dep. Runtime-permission pattern to copy: `LauncherActivity.kt:343-359` (camera; `rememberLauncherForActivityResult(RequestPermission())`).

## VERIFIED on-device: the broker loopback is auth-walled (pivotal)
`adb forward tcp:19451 tcp:9451` then curl from Mac: **every** request (any path, no token, bogus token) returns `HTTP 401 {"error":"unauthorized"}`. The auth check runs before routing (unknown path also 401s). So `BrokerRouter.kt`'s `sessionToken` (SecureRandom, in-process, never shared with Go) walls off the whole loopback. Maps must run via the direct-Linux client (`production.go:285`, `GOOGLE_MAPS_API_KEY`) — the Android-broker path is effectively dead. **Location has no Linux fallback, so this channel can't be used without new Android<->Go auth.**

## Design fork (to settle before building)
- **Design A (maps/broker template):** clean request/response, but requires inventing an Android<->Go shared secret for the 9451 loopback (currently 401s everything). Higher risk; on a possibly-dead path.
- **Design C (device_action websocket, notification-reply template):** agent -> Go `RunOnDevice` (`handler.go:890`) sends `device_action` over the ALREADY-authenticated wss session -> Android executes -> returns `device_action_result`. Reuses a working, authenticated, proven-to-reach-Android channel. Gap: `device_action_result` body is only `{requestId, outcome}` (`handler.go:966`) with no data field, and `ProtocolCodec.deviceActionKinds` is a closed set (`ProtocolCodec.kt:598`). So the change = add a return-payload field + a new `get_location` kind + Android FusedLocationProvider handler. Additive, contained, no new auth.
- **Leaning Design C** (subtract-before-add / redesign-from-first-principles: reuse the authenticated channel instead of building a second auth system). `architect` will confirm before build.

## FINALIZED tool contract (data shape — decided, independent of transport)
Agent-facing tool name: `get_location`. **Input: none** (keep minimal; no args to misuse). The app decides fine-vs-coarse fallback internally.
Success payload (what the adapter returns to the agent):
```json
{
  "latitude": 37.4219983,
  "longitude": -122.0840000,
  "accuracyMeters": 12.5,
  "timestampMillis": 1690000000000,
  "provider": "fused",
  "address": "1600 Amphitheatre Pkwy, Mountain View, CA 94043"
}
```
`address` is optional/best-effort (Android `Geocoder`, offline-capable, no key); omit the field on geocode failure. Failure is a typed object, never a null:
```json
{ "error": "permission_denied" | "location_unavailable" | "timeout", "message": "human-readable" }
```
Transport = Design C (device_action websocket), pending wiring recon (agent aac02…) to confirm adapter→RunOnDevice handle + the payload-return protocol change. `architect` multi-model panel skipped with reason: the design space is narrow — the broker loopback is auth-walled (verified 401), so the authenticated device_action channel is the ONLY working path; a panel would not change the decision. First-principles design + source-grounding recon stand in for it.

## On-device verification plan (run after deploy; no code duplication)
1. Grant nothing first. Trigger `get_location` from the agent (send the operator a message asking for current location) → expect a runtime permission prompt to appear on the phone; deny once → expect typed `permission_denied` back to the agent (not a crash/null).
2. Grant fine location → re-ask → expect a real lat/lon within ~device accuracy, `provider` populated, and (best-effort) an `address`. Cross-check lat/lon against the phone's own Google Maps "my location" to within accuracyMeters.
3. Confirm the tool is visible to the agent: after `sync-tools.mjs` rerun on-device, the agent's tool list includes `get_location` (grep the plugin tools.json on-device or ask the agent to list its tools).
4. adb evidence: logcat shows the device_action `get_location` decode + FusedLocationProvider fix + `device_action_result` with payload. Save the logcat window to this folder.

## Design C CONFIRMED — exact change set (wiring recon, source-grounded)
Path: agent → `POST /v1/agent-tools/call` → `phoneruntime/agentbridge/bridge.go` runner.Execute(adapter). Adapter does NOT hold a session handle; it **returns a sentinel** `*adapter.DeviceWorkError{Kind,Handle,Text,Ceiling}` (`capability/adapter/device_work.go:32`). Bridge catches it (`bridge.go:392`), calls `bridge.runOnDevice` (`bridge.go:424`) → `gate.DeviceWorker.RunOnDevice` = `mobilesession.Handler.RunOnDevice` (`handler.go:890`, SYNC, 60s timeout, requestId-correlated via `devicework.Ledger`). Sends `device_action` frame over the authenticated wss → Android `LauncherSessionViewModel.handleDeviceAction` (`LauncherSessionViewModel.kt:1255-1289`) executes and returns `device_action_result`. Template kind: **`youtube_play`** (`youtube/adapter.go:140-154` + `YouTubePlaybackAction.kt` executor).

**Return path — key simplification (Laziness/Subtract-before-add):** the result reaches the agent ONLY through the existing free-text `ToolCallResult.Detail` (`agentbridge/shapes.go:61-72`). So carry the location JSON back in the existing Detail/payload path — do NOT add a new field to `ToolCallResult` or the tool-call response contract. The agent is an LLM; JSON-in-Detail is fine.

**Wire-frame gotcha:** `device_action_result` body is checked against an EXACT key set on BOTH ends (not a whitelist), so a one-sided add breaks the frame. Symmetric edits required:
- Android encode: add `payload` to the result `buildJsonObject` (`LauncherSessionViewModel.kt:1280-1288`) AND allow the key in `ProtocolCodec.kt:194-198` (`DEVICE_ACTION_RESULT` exact-key check) AND add `"get_location"` to `deviceActionKinds` (`ProtocolCodec.kt:598`).
- Go decode: add `Payload string` to inbound struct (`handler.go:967-970`), thread into the `devicework.Result` built at `handler.go:~1022` so it lands in `Result.Detail`; add `Payload string` to `devicework.Result` only if Detail can't be reused. Add `"get_location"` to `knownDeviceActionKind` (`validation.go:1069-1076`) and allow optional `payload` key in the result case (`validation.go:587-596`).
- New Go adapter pkg `capability/adapters/getlocation/` (model `youtube/adapter.go`), register in `capability/runtime/production.go:~276`.
- Android executor: new injected lambda (model `carryOutYouTubePlayback`, `LauncherSessionViewModel.kt:89-90` wired in `LauncherApplication.kt:96-97`) calling `FusedLocationProviderClient`; `get_location` branch in the `when` (`LauncherSessionViewModel.kt:1264`). Manifest `ACCESS_FINE/COARSE_LOCATION`; `play-services-location` in `build.gradle.kts`; permission gate modeled on `LauncherActivity.kt:343-351` (camera).
- Plugin: rerun `sync-tools.mjs` on-device so the agent sees `get_location`.

**Deploy is heavier than latency:** needs Go runtime rebuild + redeploy into the phone proot AND Android rebuild AND plugin resync on-device. So ship latency (Android-only) first, location second.

**Contract drift noted (pre-existing):** `open_page` decodes on Android (`ProtocolCodec.kt:598`) but is produced nowhere in Go and missing from `knownDeviceActionKind` — the two wire-schema copies have already drifted. Keep the two `get_location` copies in lockstep to avoid adding to that.

## Final design locks (grounded, then delegated for implementation)
- **Adapter = one tool.** Each adapter is exposed as one agent tool named by its manifest `ID`, with a `verb` enum param (`bridge.go:176-223`). So the tool is `{adapter:"location", verb:"read"}` — no new tool-plumbing.
- **Verb = `manifest.Read`.** `Read.RequiresPreview()` is FALSE (only Send/Order/Book/Write/Cancel/Modify require preview, `manifest.go:92`), so location reads flow Resolve→Execute with NO confirm step — exactly the on-demand foreground behavior chosen. No new verb needed (verb set is fixed: Read/Compose/Send/Order/Book/Play/Write/Cancel/Modify).
- **Outcome word reuse.** `handleDeviceActionResult` maps a FIXED outcome-word allowlist (handed_to_the_app / notification_gone / refused / failed) to a hardcoded `(done, detail)` (`handler.go:981-1002`); unknown words are rejected by the contract validator. So get_location reuses the existing valid `"handed_to_the_app"` and carries its real content in the new `payload` field — avoids rippling a new outcome word through both validators + the Android decoder. A get_location EARLY-BRANCH before the switch delivers `Result{Answered:true, Reached:Completes, Done:true, Detail: payload}`; payload IS the answer, HandsOff clamp bypassed.
- **Detail is the agent's channel.** The device-work `Result.Detail` free-text is the only field reaching the agent (via `ToolCallResult.Detail`), so location JSON in Detail needs no new tool-response contract field.
- Delegated the full implementation (Go adapter + handler/validation symmetric edits + Android FusedLocationProvider executor + manifest/deps/permission + mirrored round-trip tests) to a subagent with build gates; reviewing the diff on return. On-device verify pending the phone reconnecting.

## Post-merge adversarial review (fresh reviewer, claude-fable-5, first-principles) — 2 bugs fixed, 1 kept by design
Ran a fresh different-model reviewer over the merged diff for RUNTIME bugs unit tests can't reach. Verified its two load-bearing claims myself before acting (`minSdk = 31` in build.gradle.kts:24; `submissionScope = workScope ?: viewModelScope` at LauncherSessionViewModel.kt:105, and `workScope` is null in production, so the fetch runs on Main.immediate).
- **FIXED #1 (must-fix, latent ANR).** `DeviceLocationAction.reverseGeocode` pre-33 branch called the synchronous deprecated `Geocoder.getFromLocation(lat,lon,1)` with no dispatcher hop, on viewModelScope (Main). On API 31/32 (real supported devices; NOT the Pixel 9 which is API 34+) a GPS success would then block the UI thread for seconds → ANR risk on the feature's own happy path. Fix: wrapped that call in `withContext(Dispatchers.IO)`. Root cause per fix-root-causes was "nothing in the chain switches off Main", but only that one call actually blocks (everything else suspends), so the targeted IO hop is the precise, minimal fix.
- **FIXED #2 (hits the Pixel too).** `awaitGeocode` wired only the success lambda; `GeocodeListener.onError` kept its no-op default, so a geocode failure (no network) never resumed the continuation and the caller ate the full 3s `GEOCODE_TIMEOUT_MILLIS` before returning address-less. Fix: explicit `GeocodeListener` implementing both `onGeocode` (resume addresses) and `onError` (resume null → immediate fallback).
- **KEPT BY DESIGN #3 (my call, not a user decision).** Go get_location early-branch returns `Done:true, Reached:Completes` unconditionally and Android always sends `outcome="handed_to_the_app"` even on `permission_denied`/`timeout`; the agent learns failure only by reading the typed `{"error":...}` JSON in Detail. This is intentional and correct for an LLM-facing tool: a structured error body is richer than a bare "failed", and mapping failure to `Done:false` would require the new-outcome-word ripple through both validators + the Android decoder that the design deliberately avoids. Payload is never empty (failurePayload/successPayload always emit non-empty JSON; the empty-string constructor default is overridden in production). Recorded as a deliberate contract choice.
- Reviewer confirmed CLEAN: wire round-trip symmetry (payload optional, 1–4096 runes, same non-empty rule both ends), generation/staleness guard applied to get_location at the same 2 points as other kinds, NoFix timeout/no-fix distinguishability, no coroutine double-resume/leak, permission gate checked before any GPS call (no SecurityException path), and all 4 latency edits (markTaskWorkingOptimistically immutable+no-op-safe, warm-socket reuse rides the 20s ping-interval so it won't send blind into a dead socket, delay(6_000) gates only the background updater, pulsing glyph correctly scoped). Latency feature: clean.
